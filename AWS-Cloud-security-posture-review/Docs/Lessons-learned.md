# Cloud Posture Engineering Lessons Learned

## 1. Identity, Access, and Perimeter Isolation

### Why should root and normal administrative access be reviewed separately?
The root user account holds absolute, un-bounded authority (`*:*`) over the entire tenant ecosystem, including billing scopes, subscription closures, and account deletion paths, and its access cannot be restricted by traditional identity policies. Normal administrative users operate under specific IAM constraints that can be locked down, logged, and modified by the organization. Reviewing them separately ensures that emergency break-glass identities stay isolated, hardened, and free of programmatic access keys, while standard administrative workflows enforce role-based access.

### Why are temporary credentials safer than routine long-lived keys?
Temporary credentials generated by services like AWS STS or Identity Center carry strict, automated expiration windows (usually lasting from 1 to 12 hours) and invalidate themselves without manual intervention. Permanent long-lived access keys remain active indefinitely until an administrator explicitly rotates or deletes them. If permanent keys leak through developer error or local workstation compromise, an attacker gains permanent, unhindered access to the cloud environment until the leak is caught and remediated.

### Why does an AWS-managed policy name not prove least privilege?
An AWS-managed policy name like `SecurityAudit` or `ReadOnlyAccess` simply acts as a generic template descriptor created by the cloud vendor for broad, multi-tenant use. While it may prevent a user from making data modifications, it can still grant immense data visibility, allowing an unprivileged identity to read sensitive data across every single bucket or database in the environment. True least privilege requires crafting customer-managed policies that limit actions to specific resource ARNs, named tables, and tight execution conditions.

### What is the difference between an identity policy and a role trust policy?
An identity-based policy is attached directly to an IAM user, group, or role to define exactly *what actions* that identity can execute against various AWS resources. A role trust policy is attached to an IAM role to define *which external principals* (such as specific user accounts, federated identities, or AWS services like CloudTrail) are cryptographically permitted to assume that role in the first place. Identity policies control outbound capabilities, while trust policies govern inbound session inheritance.

### Why should account-level and bucket-level S3 public-access blocks both be reviewed?
Reviewing both levels enforces the security principle of defense-in-depth across the storage tier. The account-level Public Access Block acts as a centralized, master safety switch that blocks public internet data exposure across the entire tenant workspace, protecting the organization even if a developer makes an error down the line. Reviewing individual bucket-level blocks ensures that if the account-level block is ever accidentally altered or turned off during infrastructure changes, the data remains protected by a secondary, localized deny boundary.

## 2. Telemetry, Storage Resilience, and Risk Optimization

### Why are encryption, versioning, logging, and backup different controls?
These mechanisms represent distinct pillars of the data-protection matrix that address completely different risk scenarios. Encryption protects data confidentiality against data theft or physical hard disk volume theft. Versioning provides fast, short-term data integrity recovery, allowing teams to quickly roll back an object if it is accidentally modified or deleted. Access logging creates forensic non-repudiation trails to track read and write activity during an incident, while a backup serves as an isolated, independent snapshot used to restore entire systems after a catastrophic infrastructure crash or widespread environment failure.

### What is the difference between CloudTrail Event History and a trail?
CloudTrail Event History is a built-in console timeline that automatically records management actions for a rolling 90 days within that specific region, but it cannot be modified, encrypted, or kept for long-term storage. An active CloudTrail trail is a custom deployment that can aggregate management and data events across all AWS regions globally. A custom trail delivers logs directly to an encrypted S3 bucket, allows long-term data retention, enables log file validation signatures to prevent tampering, and can stream event logs straight to an external SIEM.

### Why is a missing paid service not automatically a vulnerability?
A vulnerability is a verified engineering flaw or missing control that leaves a system open to threat exploitation. A premium native cloud service like GuardDuty or Security Hub is simply a specific commercial tool used to automate threat detection and streamline posture monitoring. Organizations can build effective security barriers without these tools by using free tier features, custom CLI automation scripts, host-level open-source tools, or third-party log aggregators, provided their core security controls are well-configured.

### How did you protect portfolio evidence from creating a new security risk?
I protected the environment's privacy boundary by routing all raw JSON log outputs and credential reports straight to a local `private-evidence/` directory block. This folder is explicitly listed inside the **`.gitignore`** configuration file, which stops untracked system metadata files from being committed to GitHub. On top of that, any public-facing report modules use standardized aliases (like `ID-01` and `S3-01`) and strip out real account IDs, ARNs, names, and IP addresses to prevent threat actors from mapping out the account's live architecture.

### Which finding would you prioritize first and why?
I would prioritize finding **AWS-SEC-003 (Missing Multi-Region CloudTrail Trail)** first because it represents a critical gap in our forensic visibility and non-repudiation baseline. Without a persistent multi-region trail active, the security team is left blind to any historical threat activity once the default 90-day Event History window closes. Establishing an unalterable log trail must always happen before making major infrastructure or permission changes, ensuring we have a reliable audit trail to track our own remediation work.

### What evidence is required before reducing residual risk?
Per our strict cloud risk reduction rules, a residual risk score can never be lowered simply because a control has been proposed or written in a document. Lowering a risk score requires verifiable engineering evidence: the new configuration must be actively deployed in the cloud environment, a specific read-only CLI script must be run to confirm the parameters are active, and the test results must be logged in a verification report to prove the new control is working.

### What would you add for a multi-account production review?
A comprehensive enterprise-grade production review would require moving from a standalone account audit to an organizational management framework. I would leverage **AWS Organizations** to inspect master Service Control Policies (SCPs) that enforce top-down guardrails across all sub-accounts. The assessment would use centralized multi-account log forwarding to aggregate CloudTrail logs into an isolated Organization log bucket, deploy organization-wide security tools via delegated administrator accounts, and implement automated CloudFormation StackSets to continuously audit configurations across all active regions.
